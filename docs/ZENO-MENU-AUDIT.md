# Zeno menu source audit

Reference: [tfooio/zeno-hub-dist](https://github.com/tfooio/zeno-hub-dist/tree/5a3f913c937159078df5c08099ca5f37c58229c1), commit `5a3f913c937159078df5c08099ca5f37c58229c1`, inspected 2026-11-02. No license was found in the inspected README/modules; root `LICENSE` and `LICENSE.md` returned 404. Public readability is not a reuse license or live verification.

“Implemented experimental” below describes the v7 native scope, which is offline tested and not live proven. “Candidate” means an original native implementation still needs schema validation and exact readback. “Unavailable” means listing a reference endpoint does not enable it in this project. No claim of current prices, working summons, rerolls, evolution, optimal placement, Rukia availability, or successful clears follows from this audit.

## Required Dungeon observation shape

The reference reads `dungeon_data._started`, `_dead`, `_finished`, `selected_next.choice_str/lives`, `next[choice]._t/_d`, `current_shops[1]._t/data`, `_resources.money/treasure/treasure_gold`, and `_items[].id`. It calls loaded core helpers to calculate effective shop cost and luck. Native cache access should only inspect already-loaded named exports and plain fields; it must not initialize a service or invoke arbitrary getters to obtain them. Missing core/item definitions or truncated observations are an exact blocker, not an empty shop, free buy, zero keys or no owned target.

Reference `dungeon.call` accepts **any** change in a compound signature (money/chests/items/room/start/death/choice/finish). An unrelated currency update can therefore look like confirmation. Native actions need operation-specific readback: selected room transition, exact chest count decrement, offered item acquisition with permitted currency change, or exact phase dismissal. A timed-out mutation stops without automatic resend.

## Clear-first and mobile hardening

1. Separate target collection progress from combat readiness. A screenshot saying `Idol 0/1` plus a generic blocked state does not show why play cannot start. Display `target collection unavailable` when unreadable; otherwise display owned target count, then the concrete combat blocker (equipped roster, live price/scale/cap, path/terrain, start vote, round outcome). Source listing an Idol/target is not availability evidence.
2. Preserve consent boundaries through configuration load. Zeno's Core reads saved enabled toggles before feature modules build, and its loader queues itself before module loading. SaveManager autoload occurs before most feature controls exist. Native settings can persist, but settings load must not arm, start, spend or revive a revoked session; no in-flight action survives reload.
3. Stop repeated losses. Source finish replay eligibility can allow loss replay, and Dungeon death recovery can continue a failed locked choice. Record a confirmed loss once; stop the controller and request a new explicit arm. Never “recover” by starting a fresh key-consuming run. Positive exact target collection readback should stop further farming.
4. Serialize the match boundary. Source independently runs finish handler, Dungeon handler, macro, autoplay, ability, sell-at-wave and lobby workers. It contains coordination checks, but not a single transport owner. Native chooses one active controller and one pending mutation; reject external Zeno presence; disarm on unanticipated stage/roster changes.
5. Avoid global hooks, unbounded polling and shared-service patches. Macro uses `hookmetamethod`; Lobby disables reveal listeners and replaces a message function; Place Anywhere replaces the placement service's `on_place` method. Dungeon temporarily listens to every server-to-client RemoteEvent for chest reporting. Performance scans workspace descendants and mutates/deletes world content. Native should cache named sources, cap map candidates and yields, refresh slow-changing labels less often and disconnect all listeners on close.
6. Use truthful progress text: waiting for cash, waiting for start, placing slot N, waiting for exact placement, known maximum, unsupported field, failed readback, defeat, finished. Keep Stop visible on touch screens. Profile buttons must only change nonconsumptive settings, show their effect and leave automation OFF.

## Small useful additions and deferred work

Good near-term additions are original Balanced / economy / damage settings profiles; a bounded start-wave action with `VotingFinished` readback; readable slot cost/cap/missing-data feedback; one local round record with win/loss and the last exact blocker; and a visible continuation opt-in/armed/expired state. Profiles require no new remote. A start vote still needs a current observed endpoint and strict round guard. Wave skip is a separate candidate; persistent game auto-skip is a broader account-setting change.

Defer premium summons, exchanges, inventory sale, capsule consumption, new Dungeon starts, shrine acceptance, general party/joiner automation, full macro compatibility, complex smart ability strategies and destructive performance modes. Their listing here is a roadmap of source capabilities, not a readiness grant. Reroll and evolution implementations were **not found in the inspected menu modules**; the collection's trait/evolution fields do not establish their protocols or consumption costs.
